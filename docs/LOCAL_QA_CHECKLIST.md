# ISHTAR — Local QA Checklist قبل الدمج

> Inherited baseline checklist/implementation notes. Not evidence that ISHTAR runtime checks have passed; see the root README for current status.

> الهدف من هذا الملف: فحص كل السيناريوهات المهمة بعد آخر تعديلات: Variant Builder، الطلبات، المخزون، sold count، التوصيل اليدوي، تتبع الطلبات، لوحة الأدمن، ورقم واتساب اختياري.

## 0) تجهيز البيئة محلياً

### 0.1 قبل التشغيل
- [ ] انسخ `.env.example` إلى `.env` وعدّل القيم حسب جهازك.
- [ ] تأكد أن PostgreSQL شغال وأن `DATABASE_URL` صحيح.
- [ ] تأكد أن المنفذ المستخدم في `DATABASE_URL` مطابق للـ PostgreSQL عندك.

### 0.2 أوامر التجهيز
شغّل بالترتيب:

```bash
npm install
npm run db:generate
npm run db:push
npm run db:backfill-delivery-fee-status
npm run db:backfill-inventory-ledger
npm run db:backfill-sold-count
npm run db:audit-commerce
npm run typecheck
npm run lint
npm run build
npm run dev
```

> ملاحظة: إذا رجّع `db:audit-commerce` أخطاء، لا تعمل merge قبل مراجعتها.

## 3) فحص Checkout

### 3.1 طلب بدون واتساب
- [ ] أضف منتج للسلة.
- [ ] افتح `/checkout`.
- [ ] عبّئ الاسم، الجوال، المدينة، المنطقة، العنوان.
- [ ] اترك رقم واتساب فارغ.
- [ ] تأكد أن summary يعرض: الإجمالي قبل التوصيل.
- [ ] أرسل الطلب.
- [ ] يجب أن ينجح الطلب وينتقل إلى `/order-success?order=...`.
- [ ] افتح الأدمن وتأكد أن الطلب موجود بدون رقم واتساب.

### 3.2 طلب مع واتساب مختلف
- [ ] كرر طلب جديد.
- [ ] أدخل رقم جوال عادي.
- [ ] أدخل رقم واتساب مختلف في الحقل الاختياري.
- [ ] أرسل الطلب.
- [ ] افتح تفاصيل الطلب في الأدمن.
- [ ] تأكد أن رقم الواتساب ظاهر.
- [ ] تأكد أن رقم الواتساب يظهر في قائمة الطلبات وCSV والفاتورة/التجهيز إذا موجود.

### 3.3 Validation
- [ ] حاول إرسال الطلب بدون اسم.
- [ ] حاول بدون جوال.
- [ ] حاول بدون مدينة/منطقة/عنوان.
- [ ] جرّب رقم واتساب قصير أو غير منطقي.
- [ ] تأكد أن رسائل الخطأ واضحة وموبايل-first.

## 5) فحص تتبع الطلبات من نفس الجهاز

### 5.1 الطلبات المحفوظة محلياً

- [ ] اضغط `تتبع الطلب` من الكارد.
- [ ] يجب أن تظهر نتيجة التتبع بدون كتابة رقم الطلب والجوال.

### 5.2 التتبع اليدوي
- [ ] أدخل رقم طلب صحيح + رقم الجوال.
- [ ] تأكد أن النتيجة تظهر.
- [ ] أدخل رقم جوال خطأ.
- [ ] تأكد أن النظام لا يعرض تفاصيل الطلب.

### 5.3 أزرار الطلبات المحلية
- [ ] اضغط `نسخ الرقم` وتأكد أنه ينسخ.
- [ ] اضغط `تحديث الحالات` وتأكد أن الحالة تتحدث.
- [ ] اضغط `إخفاء` على طلب واحد.
- [ ] تأكد أنه اختفى من القائمة فقط، ولم يُحذف من الأدمن.
- [ ] اضغط `إخفاء الكل`.
- [ ] تأكد أن هناك تأكيد قبل الحذف.
- [ ] أكّد الإخفاء وتأكد أن القائمة أصبحت فارغة.

## 6) فحص Product Variant Builder في الأدمن

### 6.1 إنشاء منتج جديد
- [ ] افتح `/admin/products/new`.
- [ ] أدخل بيانات المنتج الأساسية.
- [ ] أضف لونين مثل: أحمر وأسود.
- [ ] أضف مقاسين مثل: S و M.
- [ ] أدخل السعر الافتراضي والكمية وحد المخزون.
- [ ] اضغط Generate variants.
- [ ] يجب أن يظهر 4 variants.
- [ ] تأكد أن SKU مولّد بشكل نظيف.
- [ ] عدّل SKU يدوياً لأحد الصفوف.
- [ ] عدّل كمية لأحد الصفوف.
- [ ] احفظ المنتج.
- [ ] افتح المنتج في storefront وتأكد أن الألوان والمقاسات تظهر.

### 6.2 منع التكرار
- [ ] حاول إنشاء SKU مكرر داخل نفس المنتج.
- [ ] يجب أن تظهر رسالة خطأ.
- [ ] حاول تكرار نفس اللون + المقاس كـ active variant.
- [ ] يجب أن تظهر رسالة خطأ.
- [ ] حاول نشر منتج ACTIVE بدون أي variant active.
- [ ] يجب أن يمنع النظام ذلك.

### 6.3 تعديل منتج موجود
- [ ] افتح منتج موجود فيه variants.
- [ ] تأكد أن IDs القديمة لا تضيع.
- [ ] عدّل سعر variant.
- [ ] عدّل كمية variant.
- [ ] احفظ.
- [ ] افتح سجل المخزون وتأكد أن تغيير الكمية سجل Manual Adjustment.
- [ ] احذف/أزل variant محفوظ سابقاً من الفورم.
- [ ] تأكد أنه لا يُحذف من DB، بل يصبح inactive.

## 7) فحص المخزون Inventory

### 7.1 خصم المخزون عند الطلب
- [ ] افتح منتج جديد واعرف كمية variant قبل الطلب.
- [ ] اطلب منه كمية 5.
- [ ] ارجع للأدمن وافتح المنتج/المخزون.
- [ ] تأكد أن الكمية نقصت 5.
- [ ] تأكد أن InventoryLog فيه حركة خروج مرتبطة بالطلب.

### 7.2 sold count
- [ ] بعد طلب 5 قطع، افتح كارد المنتج في التصنيف.
- [ ] يجب أن يظهر `+5 طلب` أو يزيد حسب الطلبات السابقة.
- [ ] شغّل `npm run db:backfill-sold-count` لو في بيانات قديمة.
- [ ] شغّل `npm run db:audit-commerce` وتأكد عدم وجود errors.

### 7.3 الإلغاء
- [ ] من الأدمن، افتح طلب جديد قبل الشحن.
- [ ] ألغِ الطلب.
- [ ] تأكد أن المخزون رجع.
- [ ] تأكد أن soldCount نقص بدون ما ينزل تحت صفر.
- [ ] تأكد أن InventoryLog فيه حركة استرجاع.
- [ ] حاول إلغاء نفس الطلب مرة ثانية أو تحديث الصفحة ثم الإلغاء.
- [ ] يجب ألا يرجع المخزون مرتين.

### 7.4 تعطيل variant
- [ ] افتح صفحة المخزون.
- [ ] جرّب تعطيل آخر variant نشط لمنتج ACTIVE.
- [ ] يجب أن يمنع النظام العملية برسالة واضحة.
- [ ] أضف variant نشط آخر أو حول المنتج لمسودة، ثم جرّب.

## 8) فحص التوصيل Delivery Fee Flow

### 8.1 إنشاء الطلب
- [ ] أنشئ طلب جديد.
- [ ] افتح تفاصيل الطلب في الأدمن.
- [ ] يجب أن تكون حالة التوصيل: بانتظار التحديد.
- [ ] total يجب أن يساوي subtotal فقط.

### 8.2 منع الشحن قبل التوصيل
- [ ] حاول تحويل الطلب إلى SHIPPED قبل تحديد التوصيل.
- [ ] يجب أن يمنع النظام العملية.
- [ ] حاول طباعة الفاتورة النهائية.
- [ ] يجب أن تكون مقفولة أو يظهر تنبيه.
- [ ] قائمة التجهيز يجب أن تبقى متاحة.

### 8.3 تحديد سعر التوصيل
- [ ] أدخل سعر توصيل مثل 10.
- [ ] احفظ.
- [ ] تأكد أن deliveryFeeStatus صار SET.
- [ ] تأكد أن total صار subtotal + deliveryFee.
- [ ] افتح صفحة التتبع وتأكد أن الإجمالي يظهر صحيحاً.
- [ ] اطبع الفاتورة وتأكد أن التوصيل ظاهر.

### 8.4 توصيل مجاني
- [ ] أنشئ طلب آخر.
- [ ] اختر توصيل مجاني من الأدمن.
- [ ] تأكد أن deliveryFeeStatus صار FREE.
- [ ] تأكد أن deliveryFee = 0.
- [ ] تأكد أن الفاتورة تعرض مجاني.

### 8.5 قفل التعديل بعد الشحن
- [ ] بعد تحديد التوصيل، حول الطلب إلى SHIPPED.
- [ ] حاول تعديل التوصيل.
- [ ] يجب أن يكون التعديل مقفولاً.
- [ ] حول الطلب إلى DELIVERED وتأكد أنه ما زال مقفول.
