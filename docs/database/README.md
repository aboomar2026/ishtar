### محتوى المجموعات الاختبارية

أناقة يومية 40، لمسة جمال 34، هدية بمحبة 39، للعروسة 39، العناية بالجسم 6، إطلالة سهرة 36. نفس المنتج قد ينتمي لأكثر من مجموعة؛ الاتحاد يغطي 100 منتج ولا ينسخ المنتجات أو مخزونها. أول ثلاث مجموعات معدّة للظهور في الرئيسية. الأعداد الظاهرة تعتمد على نشر المنتجات وتفعيل تصنيفاتها. إعادة تشغيل الملف تحفظ الأسماء والإخفاء والترتيب والعضويات التي عدّلها الأدمن لاحقاً؛ لا تعيد العضويات المحذوفة يدوياً.

## قاعدة موجودة: تحديث schema دون إعادة تهيئة

1. حدّد قاعدة الهدف والبيئة الصحيحة من إعدادات الخدمة، دون لصق رابط الاتصال في المحادثة أو Git.
2. احتفظ بنسخة احتياطية قابلة للاسترجاع قبل تحديث قاعدة تحتوي بيانات فعلية.
3. قارن الحالة باستخدام ملف التحقق للقراءة فقط، ثم راجع الملفات الناقصة في الجدول أعلاه. RLS=false في التقرير ليس موافقة على إتاحة بيانات الجدول؛ الملفات الحالية تضبط حماية جداولها المحددة فقط، وليست تدقيقاً لجميع سياسات القاعدة.
4. طبّق ملفات schema اللازمة فقط بعد المراجعة، كمالك الجداول أو دور خادم مناسب. شغّل كل ملف كاملاً في تبويب SQL؛ ملفات المنتجات تستخدم DO واحدة حتى لا تضيع الجداول المؤقتة بين التعليمات.
5. إصلاح اسم الأدمن والنصوص اختياري حسب البيانات. بيانات الـ100 منتج والمجموعات ليست migrations مطلوبة للتشغيل.
6. تحقّق من النتائج والتطبيق بعد كل مجموعة مترابطة من الخطوات. `Success. No rows returned` متوقع لأوامر DDL، وليس خطأ ولا إثباتاً لوجود محتوى.

## الانتقال لقاعدة جديدة أو خطة مدفوعة

**ترقية خطة نفس المشروع تختلف عن الانتقال إلى مشروع/خادم جديد.** إذا بقيت القاعدة نفسها لا تعِد الاستيراد أو الـseed؛ تحقّق من endpoint والإعدادات حسب التغيير الفعلي.

للنقل الحقيقي مع الحفاظ على البيانات:

1. احتفظ بإصدار التطبيق/commit المتوافق ونسخة احتياطية لقاعدة المصدر. استخدم إجراء النسخ والاستعادة الموثّق لدى مزوّدك أو أدوات PostgreSQL المناسبة لإصداري المصدر والهدف، ثم اختبر الاستعادة على هدف منفصل قبل التحويل.
2. انقل **schema والبيانات والفهارس والقيود والتسلسلات/الافتراضات وسياسات RLS المطلوبة**، مع مراجعة المالكين والأدوار والصلاحيات على الهدف. لا تنسخ مخططات Supabase الداخلية وملكية الخدمة عشوائياً إلى مزوّد مختلف. ملفات SQL هنا مرجع للتغييرات اليدوية وليست بديلاً عن backup/restore.
3. حافظ على IDs والروابط الحالية. يشمل النقل Category/Product/Images/Variants وInventoryLog والعملاء والطلبات وتفاصيلها وحالتها، وAdminUser (التجزئات محفوظة في قاعدة البيانات، لا في Git)، وBanner/HeroSettings، وجداول Collection وCollectionProduct وProductComplement، وجداول التنبيهات الثلاثة، وأي جداول تشغيلية أخرى مستخدمة في schema.
4. ملفات إنشاء الهيرو لا تحفظ نصوص/صور/اختيار الهيرو الحالي؛ هذه في `HeroSettings.config`. وكذلك صور وترتيب المجموعات والمنتجات تحتاج نقل صفوف البيانات، لا إعادة تشغيل seed فقط.
5. روابط Cloudinary وDummyJSON في صفوف الصور ليست ملفات صور داخل PostgreSQL. احتفظ بحساب/أصول Cloudinary وإعداداته، وأي تخزين خارجي مطلوب، أو خطط لنقل الوسائط بشكل مستقل. صور عينات الاختبار روابط خارجية وليست مرفوعة تلقائياً إلى Cloudinary.
6. أوقف إنشاء طلبات جديدة وعامل إرسال التنبيهات خلال نقطة القطع المتفق عليها، أو استخدم آلية مزامنة/ترحيل يضمنها مزوّدك. النقل والاختبار والتحويل الفعلي يحتاج مهمة منفصلة؛ هذا التوثيق لا ينفذها.
7. اختبر نسخة الهدف ببيئة معزولة. لا ترسل أحداث التنبيهات القديمة تلقائياً ولا تشغّل worker على نسختين. راجع SENT/UNCERTAIN والرسائل التي قد تكون أُرسلت بالفعل قبل استئناف أي queue.
8. حدّث `DATABASE_URL` و`DIRECT_URL` في نطاقات Netlify المقصودة فقط، مع SSL/اتصال مناسب وأدوار Prisma. لا تحفظ القيم الفعلية في المستودع. تحقّق أيضاً من origin العام وCloudinary وسر جلسات الأدمن ومتغيرات Telegram/outbox؛ هذه إعدادات خارج قاعدة البيانات.
9. بعد التأكد من الاستعادة والصلاحيات نفّذ التحقق للقراءة فقط، وقارن أعداد الجداول والمجاميع والمخزون وعينات IDs، ثم افحص دخول الأدمن والمنتجات والهيرو والمجموعات والبحث والطلبات. اختبار شراء حقيقي/Telegram ليس جزءاً من هذا السجل.
10. احتفظ بالمصدر وخطة رجوع. بعد قبول كتابات جديدة على الهدف، الرجوع لمصدر قديم يفقد تلك الكتابات ما لم تُصالحها؛ لا تعِد endpoint تلقائياً دون مراجعتها.

### قاعدة اختبار فارغة تماماً

لإعادة تجربة schema فقط على PostgreSQL محلي/معزول وفارغ، يمكن توليد SQL دون اتصال بقاعدة حقيقية:

```bash
npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script > /tmp/ishtar-schema-reference.sql
```

هذا **مرجع مولّد من الكود** وليس ملفاً تاريخياً شُغّل على سوبابيس، ولا يحتوي البيانات أو كل قيود SQL اليدوية. لا تنفذه على قاعدة موجودة. توجد قيود مثل `OrderNotification_deliveryStatus_check` و`OrderNotification_attempts_check` و`ProductComplement_no_self` لا يعبّر عنها Prisma schema؛ يلزم الحفاظ عليها عبر الاستعادة أو مراجعة ملفات SQL الأصلية. CREATE TABLE IF NOT EXISTS وحده لا يضيف قيود جدول موجود.

لذلك مسار النقل الموصى به لقاعدة فعلية هو استعادة نسخة كاملة والتحقق، وليس `db push` أو إعادة بذرة الاختبار. لا يوجد حالياً `prisma/migrations` baseline موثق يسمح باعتبار `migrate deploy` كافياً.

## مصدر الثقة والتحقق

- سجل التنفيذ يستند إلى رسائل المالك وقرائن التسليم، لا إلى تخمين تشغيل كل ملف في المستودع.
- الإصدار الحالي المصحح من ملفات الاستيراد والإصلاح هو المرجع؛ ليس نسخة أول أمر SQL الذي رُفض. توليده من [`generate-test-products-sql.ts`](../../scripts/generate-test-products-sql.ts) ومصدره [`test-products.json`](../../scripts/fixtures/test-products.json).
- اختبارات الملفات تعمل على PostgreSQL مؤقتة: `npm run test:test-products` و`npm run test:collections`، واختبار تجميع المرجع أدناه. لا تستخدم اتصال المتجر ولا ترسل Telegram.
- يمكن تعديل حالة صف واحد من السجل لاحقاً عند مشاركة نتيجة تشغيله. لا نخلط «محفوظ في Git» مع «مطبّق على القاعدة».

```bash
node --import tsx --test tests/database-reference.integration.test.ts tests/collections-seed.integration.test.ts
```
